✅ ArrayBuffer & Typed Arrays in JavaScript
ArrayBuffer and Typed Arrays are part of the JavaScript Binary Data API, useful for handling raw binary data — such as when dealing with files, WebSockets, or low-level protocols like WebAssembly.

🧠 What is an ArrayBuffer?
A low-level, fixed-length binary buffer of raw memory.
It is just a container; you can't read or write directly to it.
Size is in bytes.

🧠 What are Typed Arrays?
Views over ArrayBuffer for reading/writing specific data types.
Examples: Uint8Array, Float32Array, Int16Array, etc.
All Typed Arrays use little-endian by default.

| Constructor    | Element Size | Description             |
| -------------- | ------------ | ----------------------- |
| `Int8Array`    | 1 byte       | 8-bit signed integer    |
| `Uint8Array`   | 1 byte       | 8-bit unsigned integer  |
| `Int16Array`   | 2 bytes      | 16-bit signed integer   |
| `Uint32Array`  | 4 bytes      | 32-bit unsigned integer |
| `Float32Array` | 4 bytes      | 32-bit floating point   |
| `Float64Array` | 8 bytes      | 64-bit floating point   |


const buffer = new ArrayBuffer(4);         // 4 bytes = 32 bits
const view = new Int32Array(buffer);       // 32-bit signed integer

view[0] = 42;

console.log(view[0]);                      // 42
console.log(buffer.byteLength);            // 4

✅ What is Client-Side Routing?
Client-Side Routing means:

The browser does not request a new HTML page from the server on every navigation.
Instead, JavaScript dynamically updates the view by modifying the URL and rendering components.
It relies on the History API (pushState, replaceState) or Hash-based routing (#)

⚙️ How Client-Side Routing Works

User navigates → full page reload

Server sends new HTML for every route

⚡ Client-Side Routing:
User navigates → JS intercepts route change
URL is updated via history.pushState
A new component/view is rendered instantly
No full page reload

🧠 What is a Generator Function?
A Generator Function allows you to pause and resume execution using the yield keyword.

It returns a Generator object, which is an iterator — each call to .next() runs the function up to the next yield.


function* generatorFunc() {
  yield 1;
  yield 2;
  return 3;
}

const gen = generatorFunc();
console.log(gen.next()); // { value: 1, done: false }
console.log(gen.next()); // { value: 2, done: false }
console.log(gen.next()); // { value: 3, done: true }

| Feature     | Description                                     |
| ----------- | ----------------------------------------------- |
| `function*` | Declares a generator                            |
| `yield`     | Pauses function and sends a value               |
| `next()`    | Resumes execution and returns `{ value, done }` |
| `return`    | Ends the generator and returns value            |


| Use Case            | How Generator Helps                       |
| ------------------- | ----------------------------------------- |
| Custom Iterators    | Yield values lazily in a loop             |
| Infinite sequences  | e.g. Fibonacci, random numbers            |
| Async control flows | Power behind `redux-saga` (via `yield`)   |
| Pause-heavy tasks   | Stream large data chunks without blocking |


function* dialogue() {
  const name = yield 'What is your name?';
  yield `Hello, ${name}`;
}

const convo = dialogue();
console.log(convo.next().value);           // 'What is your name?'
console.log(convo.next('Sonam').value);    // 'Hello, Sonam'

✅ What Is Memory Management?
Memory management in JavaScript refers to:
Allocating memory when variables/objects are created.
Releasing memory that’s no longer needed — done via Garbage Collection (GC).
JavaScript uses automatic memory management, meaning the engine (like V8) handles allocation and deallocation.

🧹 What Is Garbage Collection?
Garbage Collection is the process of finding and freeing up memory occupied by values that are no longer reachable.

🔍 How Does It Work?
🔗 Reachability-Based Garbage Collection
An object is considered reachable if:

It is in the global scope.
It is referenced by a local variable or another reachable object.
Anything not reachable is garbage collected.

| Issue                  | Example                                     |
| ---------------------- | ------------------------------------------- |
| **Memory leaks**       | Retaining references longer than needed     |
| **Closures overused**  | Holding variables in memory unintentionally |
| **Forgotten timers**   | `setInterval` never cleared                 |
| **Detached DOM nodes** | Removed from DOM but still in JS memory     |

JavaScript engines like V8 use the Mark-and-Sweep algorithm for garbage collection.
🔄 How it Works (Step-by-Step):

Mark Phase
The engine starts from "roots" (e.g. global variables, active function calls).
It recursively marks all objects reachable from these roots.

Sweep Phase
All unmarked objects are considered unreachable.
These objects are then removed (freed) from memory.

📌 Roots in JavaScript:
| Root Type         | Examples                         |
| ----------------- | -------------------------------- |
| Global references | `window`, `globalThis`, `global` |
| Stack variables   | Variables in current scope       |
| Closures          | Enclosed variables in functions  |


🚫 Memory Leak Scenarios (Mark-and-Sweep won’t help if...):
Timers not cleared (setInterval)
Event listeners not removed from DOM
Closures that unintentionally hold variables

✅ What Are They?
WeakMap: A collection of key-value pairs where keys must be objects, and references are weak.

WeakSet: A collection of objects only, also with weak references.

“Weak” means they don’t prevent garbage collection if there are no other references to the object.

| Feature             | `WeakMap`                             | `WeakSet`                  |
| ------------------- | ------------------------------------- | -------------------------- |
| Stores              | Key → value pairs                     | Object values only         |
| Keys/Values         | Only **objects** as keys              | Only **objects** as values |
| Garbage Collectable | ✅ Yes (if object becomes unreachable) | ✅ Yes                      |
| Iterable?           | ❌ No                                  | ❌ No                       |
| Size property?      | ❌ No `.size` or `.clear()`            | ❌ No `.size` or `.clear()` |


const wm = new WeakMap();
let obj = { name: "Sonam" };

wm.set(obj, "data");
console.log(wm.get(obj)); // 'data'

obj = null; // original object is now GC eligible


const ws = new WeakSet();
let user = { id: 1 };

ws.add(user);
console.log(ws.has(user)); // true

user = null; // object becomes GC eligible

| Caching / memoization        | Auto-clean cache when object is gone    |
| Hiding internal object state | Keep private data without exposing it   |

✅ What is Shadow DOM?
The Shadow DOM is a browser feature that allows developers to encapsulate a portion of the DOM, keeping its styles and structure isolated from the rest of the document.

It’s part of the Web Components spec and allows for style + behavior encapsulation.

🔧 Why Use Shadow DOM?
Prevent CSS/style leakage into or out of components

Encapsulate internal structure and logic

✅ What is Shadowing?
Shadowing happens when a variable declared in a local (inner) scope has the same name as a variable in an outer scope.

The inner variable "shadows" the outer one — making the outer one inaccessible within that inner scope.

let message = "Global";

function showMessage() {
  let message = "Local"; // shadows the outer `message`
  console.log(message);  // "Local"
}

showMessage();
console.log(message);    // "Global"

You cannot shadow let or const with var in the same scope due to temporal dead zone and scope conflict.
